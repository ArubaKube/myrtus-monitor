Node Type Configuration

Every node in a Myrtus federation has a role — cloud, fog, or edge. This page explains how to set it.

The node type is reported by the node-monitor DaemonSet and pushed to the knowledge base as part of each node's metrics. It determines how the node is classified in the resource registry and is required for the federation to correctly route and allocate workloads.

There are two ways to configure it:

  • Helm value (nodeMonitor.nodeType) — the standard approach. Set once at deploy time, applies to all nodes in the cluster.
  • Node label (myrtus.io/node-type) — advanced. Set per-node at any time without touching the Helm release. Takes precedence over the Helm value when present.

For most deployments, the Helm value is all you need. The node label is useful when different nodes in the same cluster play different roles, or when a node's role changes after the initial deploy.

How it works

When the node-monitor pod starts, before initializing any collectors, it queries the Kubernetes API for the node object it is running on and reads the myrtus.io/node-type label. The lookup runs in a background thread with a 10-second hard timeout so the pod always starts, even if the API is unreachable.

pod startup log — label found 
INFO     Resolving node type for node 'my-node' (fallback=cloud)
DEBUG    Loading in-cluster K8s config...
DEBUG    In-cluster config loaded, reading node 'my-node'...
DEBUG    Node labels: {'myrtus.io/node-type': 'fog', ...}
INFO     node_type resolved from node label 'myrtus.io/node-type': fog
INFO     Initializing collectors...
pod startup log — label absent, fallback used 
INFO     Resolving node type for node 'my-node' (fallback=cloud)
DEBUG    Loading in-cluster K8s config...
DEBUG    In-cluster config loaded, reading node 'my-node'...
DEBUG    Node labels: {'kubernetes.io/hostname': 'my-node', ...}
DEBUG    Label 'myrtus.io/node-type' not set on node 'my-node', using --node-type fallback
INFO     Initializing collectors...

Resolution order

The node type is resolved in the following priority order at pod startup:

#SourceCondition
1 myrtus.io/node-type node label Label is present on the node object
2 nodeMonitor.nodeType Helm value Label absent, or K8s API call fails / times out
The fallback to the Helm value is always safe. If the K8s API is unreachable, the lookup times out after 10 seconds and the pod continues with the Helm-provided type.

Via Helm value (default)

The simplest way to assign a node type is through the Helm chart at deploy time. The value nodeMonitor.nodeType is passed directly as the --node-type argument to every node-monitor pod in the DaemonSet. This is the baseline — it applies uniformly to all nodes in the cluster unless overridden individually by a node label.

This approach works well when all nodes in a cluster share the same role (e.g. a dedicated cloud cluster or a dedicated edge cluster), or when you want a safe default that nodes fall back to if their label is later removed.

charts/myrtus-monitor/values.yaml
nodeMonitor:
  nodeType: "cloud"   # cloud | fog | edge — applied to all nodes
Shell — install or upgrade
helm upgrade --install myrtus-monitor charts/myrtus-monitor \
  --namespace myrtus-system --create-namespace \
  --set nodeMonitor.nodeType=cloud \
  --set global.liqoClusterId=my-cluster \
  --set global.kbEndpoint=http://kb:8080

The DaemonSet translates this value into a CLI argument for each pod:

Rendered DaemonSet args (excerpt)
args:
  - "--node-name=$(NODE_NAME)"
  - "--node-type=cloud"      # from nodeMonitor.nodeType
  - "--liqo-cluster-id=my-cluster"
  - "--kb-endpoint=http://kb:8080"

At startup, each pod attempts to read its node's myrtus.io/node-type label. If the label is absent, cloud (the Helm value) is used as-is. The pod logs confirm this:

pod startup — no label, Helm value used 
INFO     Resolving node type for node 'my-node' (fallback=cloud)
DEBUG    Loading in-cluster K8s config...
DEBUG    In-cluster config loaded, reading node 'my-node'...
DEBUG    Label 'myrtus.io/node-type' not set on node 'my-node', using --node-type fallback
INFO     Initializing collectors...
INFO     All collectors initialized successfully.
DEBUG    {'node_name': 'my-node', 'node_type': 'cloud', 'liqo_cluster_id': 'my-cluster', ...}
Changing nodeMonitor.nodeType in Helm requires a helm upgrade and a DaemonSet rollout. If you need to change the type of individual nodes frequently, use the label override instead.

Via node label (advanced)

When nodes in the same cluster have different roles — for example a cluster with both cloud gateway nodes and fog compute nodes — the Helm value alone is insufficient. The myrtus.io/node-type node label lets you assign a type to each node individually, overriding the Helm value, without touching the Helm release.

The label is read once at pod startup. To apply a change to a running pod, update the label and restart the pod. All other pods in the DaemonSet are unaffected.

Assigning a type to a node

bash 
$ kubectl label node my-node myrtus.io/node-type=fog --overwrite
node/my-node labeled

$ kubectl rollout restart daemonset myrtus-monitor-node-monitor -n myrtus-system
daemonset.apps/myrtus-monitor-node-monitor restarted

$ kubectl logs -f -l app.kubernetes.io/name=myrtus-monitor-node-monitor -n myrtus-system
INFO     Resolving node type for node 'my-node' (fallback=cloud)
DEBUG    Loading in-cluster K8s config...
DEBUG    In-cluster config loaded, reading node 'my-node'...
DEBUG    Node labels: {'myrtus.io/node-type': 'fog', 'kubernetes.io/hostname': 'my-node', ...}
INFO     node_type resolved from node label 'myrtus.io/node-type': fog
INFO     Initializing collectors...
DEBUG    {'node_name': 'my-node', 'node_type': 'fog', 'liqo_cluster_id': 'my-cluster', ...}

Reverting to the Helm value

Remove the label to revert the node to the type defined in the Helm chart.

bash 
$ kubectl label node my-node myrtus.io/node-type-
node/my-node unlabeled

$ kubectl rollout restart daemonset myrtus-monitor-node-monitor -n myrtus-system

Mixed-role cluster example

Deploy once with a default type, then label individual nodes as needed:

bash — heterogeneous cluster setup 
# Deploy with cloud as the default for all nodes
$ helm upgrade --install myrtus-monitor charts/myrtus-monitor \
    --set nodeMonitor.nodeType=cloud ...

# Override specific nodes
$ kubectl label node node-fog-1  myrtus.io/node-type=fog  --overwrite
$ kubectl label node node-edge-1 myrtus.io/node-type=edge --overwrite

# Restart to apply
$ kubectl rollout restart daemonset myrtus-monitor-node-monitor -n myrtus-system

To remove the label and revert to the Helm value:

bash 
$ kubectl label node my-node myrtus.io/node-type-
node/my-node unlabeled

Skip inference

Pass --skip-node-type-inference to bypass the K8s label lookup entirely and use --node-type directly. This is the default for local development targets (run-node-example, docker-run-node-example) where no cluster is present.

bash 
$ node-monitor \
    --node-name my-node \
    --node-type cloud \
    --skip-node-type-inference \
    --liqo-cluster-id my-cluster \
    --kb-endpoint http://kb:8080

Kind cluster

The kind integration uses a local single-node cluster named myrtus-test. The image is built from local source and loaded directly into kind — no registry push needed. All kind targets are self-contained and use the context kind-myrtus-test.

Automated tests

Runs both scenarios end-to-end: cluster creation, both test scenarios, and teardown.

bash 
$ make kind-test-all

--- Scenario 1: node type from Helm value (nodeType=cloud) ---
✓ PASS: node_type=cloud (from Helm value)

--- Scenario 2: node type from label override (label=fog, Helm=cloud) ---
✓ PASS: node_type inferred from label (fog)
✓ PASS: node_type=fog in metrics (overrode cloud from Helm)

Custom image

By default kind tests build and use a local image tagged myrtus-monitor:kind-test. Override KIND_IMAGE_REPO and KIND_IMAGE_TAG to use a different image.

When using a published image, pull it locally first — kind load docker-image requires the image to be present in the local Docker daemon.
bash 
$ docker pull ghcr.io/arubakube/myrtus-monitor:1.2.3

$ make kind-demo \
    KIND_IMAGE_REPO=ghcr.io/arubakube/myrtus-monitor \
    KIND_IMAGE_TAG=1.2.3

Helm values reference

ValueDefaultDescription
nodeMonitor.nodeType cloud Fallback node type used when no myrtus.io/node-type label is present. Options: cloud, fog, edge.
nodeMonitor.kbDisabled false Disable the knowledge base integration. Useful for local testing when no KB endpoint is available.

CLI flags reference

FlagRequiredDescription
--node-type Yes Node type fallback value. One of cloud, fog, edge. Used when no label is set or inference is skipped.
--skip-node-type-inference No Skip the K8s label lookup and use --node-type directly. Enabled by default in local dev targets.
